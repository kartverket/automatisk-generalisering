# Design-set review, 2026-09-14

**Status:** TEMPORARY. A one-off review of DECISIONS.md, TASKS.md, 01-terminology.md, 02-runtime.md,
03-architecture.md, 04-migration.md and `template_code/ag/` before implementation starts. Not

Finding ids (F-numbers) are used across sections. Each carries a confidence and a gate: blocks
T0.1/T0.6, blocks a named later task, or no gate.

## What changes this week

- **F1. T0.6(a) measures the path production will not run.** A15.3 says the preferred ArcPy form
  is a `join_field` against a temp table with no Python-side map. T0.6(a) benchmarks only the
  packed map, so the production path (arcpy JoinField over a national-scale key table) stays
  unmeasured while a fallback gets three numbers. Add JoinField at the same three sizes to
  T0.6(a), keyed on OBJECTID, and report both. If JoinField holds, Path B stops being a gate input
  (see F24). *Blocks T0.6. High confidence.*
- **F2. A14 tier 2 has an unstated group-size limit and is what runs on the current image.** The
  lineage table is confirmed new at Pro 3.7; the image is `ghcr.io/kartverket/arcpy-linux:12.0`, so
  CONCATENATE synthesis is the live path. A15.5's own worst case (every road in a partition
  dissolved into one blob) puts 10^5 to 10^6 ids into one concatenated text cell. The tool page
  says nothing about length or truncation. Add one case to T0.1 while the environment is up:
  dissolve with CONCATENATE over groups of 10^5 and 10^6, record whether it truncates silently,
  errors, or grows. *Blocks T4.10; cheapest to run under T0.1. High confidence it is unverified,
  medium that it fails.*
- **F7. The 10M design ceiling in A11.4a is a sizing answer and its rationale contradicts A11.4.**
  A11.4 says intra-operation churn is invisible at the boundary, so minting the exploded
  intermediate cannot pollute the graph; the net-effect collapse removes it. What actually goes
  wrong when minting from candidates is that the backward walk hits a FOREIGN handle
  (`conn_endpoints`) and yields CREATED plus DROPPED, which is exactly the A11.13/T4.13 signature
  and already detected. So the ceiling is a cost guard, which A11.4a says it is not. Separately,
  A10.1 cites "river gap generation, about 8M features" as the legitimate per-job mint worst case;
  if that is legitimate, the 10M ceiling has 1.25x headroom on a known case and A11.4a's own
  "largest basin 35x" puts a legitimate subject over it. If the 8M is the candidate set, A10.1's
  headroom is computed from a non-case. Recommendation: drop the design ceiling, keep the
  resource ceiling, rely on A12.9 plus T4.13 for the semantic error. This changes what T0.6 must
  produce (a resource-ceiling method only). *High confidence on the contradiction, medium on the
  recommendation.*
- **F9. Settle B9 now.** It blocks T0.4, T0.6(b), T3.4's map-only branch, T3.6, T3.7(a) and T6.2.
  B9(d) already forces the in-run stage output to carry `lineage_id`, and the A22 argument forces
  archive schema = working schema. What remains is only hop 2. Recommended answer: the archive
  carries `lineage_id`; publish produces the archive plus a mapped delivered copy; the delivered
  copy carries the same value under a non-identity name plus a run-id field. *Blocks T0.6(b).
  High confidence it should be settled, medium on the answer.*
- **F5 and F6 change T4.1's shape and are cheaper to fix before the grammar is written** (section
  2). Not gates on T0.x.
- **F53. The partition shadow track (T0.2, T1.1, T1.3, T1.4) is in the old code, independent of
  all lineage work, and has the longest lead time.** Start it in parallel with the gates rather
  than at positions 2 through 5.

**Scope gap.** A6.1's decisive property rests on "halo adequacy is unconditional and mechanically
tested", meaning the K=4 vs K=16 harness of 02-runtime §7.2, which 04-migration §3 calls the one
thing to start now. No task builds it. If it is out of lineage scope, say so in TASKS; today A6
cites a test that does not exist.

### Challenge details not covered above

**F4 (A10.5, T3.5).** ADR-0009 says there is no intra-pod resume, and A10.4 says retry safety
comes from wholesale replacement of the job's artifacts with the minter id reused. A10.5 then
says a midpoint restart persists the counter high-water mark "in the checkpoint" and continues
from n+1. Nothing in the design has a checkpoint. Either A10.5's first sentence is dead text and
only the "exceeding 2^32-1 fails loudly" clause survives, or it is an unrecorded reintroduction
of intra-pod resume. T3.5's acceptance criterion copies the clause. *Blocks T3.5. High
confidence.*

**F24 (A10.1, A10.3, A15.3 Path B).** Two simplifications of settled positions.

- *Generated-id layout.* A21 and A24.1 already forbid inferring anything from an id's shape,
  A10.7 already allocates disjoint ranges from one run-scoped counter for ingest, and the
  dispatch registry already exists. Handing each job a range of 2^32 from the same counter at
  dispatch is the same allocation without the sign convention or the bit arithmetic; T0.1 case
  4's "every generated id has magnitude at least 2^32" stops being a special case, a DOUBLE
  downcast no longer breaks a decode, and A25(b) becomes one interval check for all ids. The
  recorded reasons do not cover this: A10.3 rejected placeholder ids, A10.1 chose negative over a
  high bit for decode simplicity, and range allocation has no decode. Cost is a bisect over the
  registry where a shift was. *Medium confidence it is better; a direction question.*
- *Path B.* A15.3 keeps the packed map permanent because "rot is a backend property". Rot is a
  test-coverage problem, solvable with a fake adapter that lacks a join key, and every
  foreseeable backend (file gdb OBJECTID, GeoPackage fid, Postgres primary key) has an addressable
  row index. By the port file's own rule that a method with no caller is not shipped, Path B has
  no caller. Build it when a backend needs it. *Medium confidence.*

**F8 (A16, T5.1, T5.2, T6.1).** The completeness pass computes I, O, T, D over all objects in the
stage nationally. As Python sets of ints that is roughly 70 to 100 bytes per id, so 10M ids is on
the order of 1 GB, at the end of a stage where an OOMKill costs the most. The A15.5 edge's
`from_ids` in the pod buffer and the K-way log merge have the same shape. "Memory bounded
independent of dataset size" is established for the id map only. State the representation
(sorted int64 arrays with merge-based set algebra, the mechanism A15.3 already commits to) or the
constraint is silently violated. *Blocks T5.2 and T6.1. Medium-high confidence.*

**On the priority order.** It is right, and A15.3 applies it correctly. Two places quietly
optimize for something else: A12.10 lets edge-per-row cost break a tie on a semantic
declaration, and A11.4a's ceiling is a cost guard presented as a design assertion. Both are
small; naming them is the point.

## 3. Optimizations and simplifications

- **F20.** T7.4's package-coverage meta-check is import-linter's `exhaustive` option. Verified on
  a scratch copy: `containers = ag`, `exhaustive = true` reports `ag.helpers`, `ag.adapters`,
  `ag.sources`, `ag.products`, `ag.tuning`, `ag.classification_rules`, `ag.observability` as
  unlisted. 03-architecture §4.2 already names this mechanism. Delete the hand-written test and
  use `exhaustive_ignores` for the leaves.
- **F25.** A12.7's tracked iterable is fragile: `list()` at :233 already defeats it, and any
  filter or sort does. Rows read from a CARRY handle with `fields=()` already carry `lineage_id`
  in `attributes`; `write_rows` can stamp from that attribute and reject rows lacking it unless
  `mint(parents=)` is given. Same check, no hidden object identity, survives transformation. The
  recorded rejection was `Row.parents`, a new field; this uses a column that is already visible.
- **F24** (section 1): range-allocate generated ids; defer Path B.
- **F7** (above): drop the design ceiling.
- **F26.** Settle B4 now as "unique join key, checked by the adapter". A15.3 already assumes it.
- **F9** (above): settle B9 now.
- **F10, F28, F53** (above): reorder.
- Merge candidates: A22 and A23 are two paragraphs each and both migrate to the same places as
  A24; one item. A11.4 and A11.4a are one rule and its enforcement gap; after F7 the gap closes
  and A11.4a shrinks to the FillLineGaps worked case.
- **F17.** A15.3's "subject read in map order" needs `read_rows` to guarantee ascending
  native-index order, or the facade sorts. Neither T3.1 nor T2.x states it. A monotonic-key
  assertion in the read loop is one line and replaces the code-review point. *Blocks T4.5.*
- **F11.** A9.1's 1:1 uniqueness assertion has no task. Count versus distinct count per CARRY
  output in the boundary sweep. Assign to T4.6.
- **F3.** T3.7(a) multiset equality is unsatisfiable in a partition pod: stage entry sees a
  partition (subset plus halo), not the whole dataset; equality with the map's full
  `new_lineage_id` column only holds over the whole dataset, which exists only in fan-out after
  the join. Move (a) to fan-out; leave pods with the (b) range check and A13's existence check.
  *Blocks T3.7. High.*
